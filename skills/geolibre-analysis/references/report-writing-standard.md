# GeoLibre 分析報告強制格式

本文件定義 `report.md` 的**強制寫法**。

設計基準採用既有 GeoLibre 分析報告的完整結構，而不是摘要式、簡報式或過度口語化的報告。

## 核心原則

1. `report.md` 是正式分析報告，不是簡短摘要。
2. 不得因為「白話化」而省略分析方法、分類邏輯、資料品質、限制、來源或交付檔案。
3. 不得把原本清楚的章節全部改寫成一大段敘述、單一表格或只有結論的短報告。
4. 報告必須先讓讀者快速看懂「這次分析做了什麼、用什麼條件、得到多少結果」，再往下閱讀方法與限制。
5. 新增的圖層對照、瀏覽器驗證、效能說明、總結等內容可以加入，但**只能追加，不能取代下列強制骨架**。
6. 若某一章節在個別任務不適用，也應保留章節並寫明「本案不適用」及原因，不得直接刪除。
7. 報告中的數字必須與 `summary.json`、`result.geojson`、XLSX 一致。
8. 報告必須使用繁體中文；專有名詞可保留英文或程式欄位名稱。

## 強制章節順序

`report.md` 至少必須依下列順序撰寫，章名不得任意改成其他名稱：

1. `# <分析名稱>`
2. 開頭任務摘要區塊
3. `## 方法`
4. `## 分類`
5. `## 資料品質`
6. `## 重要限制`
7. `## 資料來源`
8. `## 交付檔案`

完成以上八個固定部分後，才可依任務需要追加：

- `## 主要發現`
- `## 圖層—圖資—檔案對照`
- `## 地圖圖層說明`
- `## 效能與發布驗證`
- `## 瀏覽器畫面驗證`
- `## 後續查核建議`
- `## 總結`

## 開頭任務摘要區塊

標題之後、`## 方法` 之前，必須用短列點列出本案最重要的分析設定與結果。

至少應包含：

- 任務／task id
- 分析範圍
- 分析期間（若適用）
- 主要空間門檻
- 主要判斷條件
- 可分析母體／案件數
- 正式結果數
- 重要子結果數，例如高風險、短期重複、命中特定條件的筆數

範例：

```md
# 宜蘭縣道路工程重複施工與資源浪費風險分析

- 任務：`yilan-road-repeat-construction-audit-2026-09`
- 分析範圍：宜蘭縣
- 分析期間：2023-09-25～2026-09-25
- 空間門檻：50 公尺
- 重複施工：期間內至少 2 件
- 短期再次施工：前案完工後 180 天內
- 可分析案件：53 件
- 重複施工熱點：2 處
- 含180天短期再次施工熱點：0 處
```

此摘要必須保留，不得用長篇「主要發現」取代。

## 方法

必須回答：

- 使用哪些正式輸入資料；
- 座標系統／CRS；
- 核心 GIS 操作；
- 距離、相交、buffer、群聚、最近鄰或網路關係如何計算；
- 時間條件如何判斷；
- 哪些資料是正式判定依據；
- 哪些資料只是顯示或補充。

應以完整段落說明，不得只寫「使用 GeoLibre 進行分析」。

## 分類

若分析有任何類別、風險級別、文字關鍵詞、分數、標籤或規則式分類，都必須在此章清楚列出。

至少說明：

- 分類名稱；
- 判斷規則；
- 關鍵詞／門檻；
- 未命中時如何處理；
- 分類是否僅供查核篩選；
- 正式認定是否需要回查原始資料。

若本案完全沒有分類邏輯，保留本章並寫明「本案不適用分類規則」，再說明原因。

## 資料品質

必須量化本次資料品質，不只寫抽象限制。

至少依任務可取得情況列出：

- 原始資料筆數；
- 可分析筆數；
- 排除筆數；
- 缺日期；
- 缺座標／幾何；
- 超出期間／範圍；
- 去重前後數量；
- 來源更新日期；
- 其他會影響母體完整性的缺口。

若某項為 0，也應明確寫出 0。

## 重要限制

以列點方式清楚說明會影響解讀的限制。

至少區分：

- 公開資料與內部完整資料的差異；
- 替代來源／快取／代理來源；
- 分類推論限制；
- 空間鄰近不等同因果或違失；
- 顯示圖層與正式判定資料的差異；
- 本分析是否屬查核篩選、風險提示或正式認定。

不得把「查核優先」寫成「法定高風險」，也不得把「50 公尺鄰近」直接寫成「重複開挖已成立」。

## 資料來源

逐項列出實際使用或實際嘗試使用的來源。

至少包含：

- 提供單位；
- 資料集／服務名稱；
- URL／service endpoint；
- 資料期間／版本／更新日期；
- 當次取得日期；
- CRS；
- 在分析中的用途；
- 官方／補充／備援身分；
- 已知限制。

若資料是從既有快照或快取沿用，不得寫成「本次重新下載」。

## 交付檔案

逐項列出實際產出的檔案，至少包含：

- `map.geolibre.json`
- `overview.geojson`（若有）
- `result.geojson`
- 輸入證據／重要子集 GeoJSON
- `result.csv`
- `result.xlsx`
- `summary.json`
- `report.md`
- `report.html`（若有）
- `performance.json`
- `source-diagnostics.json`（若有）
- `source-snapshot.json`（若有）
- `map-overview.png`（若確實有產出）

每項用一句話說明用途。

未產出的檔案不得假裝存在；若新版成果契約期待但執行環境無法產出，例如沒有瀏覽器自動化而缺 `map-overview.png`，應明確寫「未產出」與原因。

## 追加章節規則

完成固定八個部分後，可以增加新版成果契約需要的內容，但應遵守：

- 「主要發現」用來解讀結果，不得重複或取代開頭任務摘要。
- 「圖層—圖資—檔案對照」應放在固定章節之後。
- 「效能與發布驗證」只補充 technical QA，不取代「資料品質」。
- 「瀏覽器畫面驗證」只說明 viewer 是否真的畫出資料，不取代「交付檔案」。
- 「總結」應簡潔收束，不應變成整份報告唯一有內容的部分。

## 禁止的退化寫法

以下視為不合格：

- 只有「主要發現／資料與方法／總結」三四個大段，卻省略固定章節；
- 把所有資料來源塞進一個表格，但沒有逐來源限制與用途；
- 只說「找到 N 筆」，沒有資料品質母體與排除數；
- 只列成果下載連結，沒有方法與限制；
- 為了讓非 GIS 使用者好懂，刪除 CRS、門檻、分類規則或來源版本；
- 把 GeoLibre 畫面是否成功載入誤當成分析正確性；
- 把公開資料篩選結果寫成行政違失或法律結論。

## QA 狀態同步規則

`report.md` 與 `report.html` 中的「瀏覽器畫面驗證／截圖驗證／Viewer QA」狀態，必須與最新一輪實際 QA 證據同步。

強制規則：

1. 若先前報告寫「尚未驗證」、「沒有瀏覽器工具」、「尚未交付」，但後續已由 Playwright 或其他等效真實瀏覽器 runner完成驗證，必須在最終交付前**重新改寫報告中的舊狀態**。
2. 不得因為報告較早產生，就保留與最新 QA 相衝突的過期敘述。
3. `report.md` 與 `report.html` 必須使用相同的 QA 最終狀態。
4. 若最新 QA 結果為 PASS，報告至少寫明：
   - 自架入口桌面／手機結果；
   - 官方備援桌面／手機結果；
   - `ready` 狀態；
   - load errors 是否為空；
   - canvas 是否可見且非白屏；
   - 預期圖層是否實際出現在 UI。
5. 若最新 QA 結果為 FAIL，報告必須寫明失敗入口與原因，不得沿用更早的 PASS。
6. QA 狀態一旦更新，應視為報告內容發生變更，必須重新寫入 repository 並重新發布。

## 驗收

在宣告 `report.md` 完成前，逐項確認：

- 有標題；
- 有開頭任務摘要；
- 有「方法」；
- 有「分類」；
- 有「資料品質」；
- 有「重要限制」；
- 有「資料來源」；
- 有「交付檔案」；
- 數字與 `summary.json` 一致；
- 結果數與 `result.geojson` 一致；
- XLSX 分析結果列數一致或已說明差異；
- 若有額外章節，不得取代上述固定章節。

任何一項未通過，`report.md` 不得標示為完成。
